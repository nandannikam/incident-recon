# ABSTRACT

**[PURPOSE]** The purpose of this project is to design and implement an educational, AI-powered
security platform that ingests fragmented operating-system and network log files from multiple
hosts and reconstructs cohesive, explainable, and interactive attack timelines. Modern Security
Operations Centre (SOC) analysts are overwhelmed by thousands of disconnected log entries — file
downloads, process executions, registry changes, and network connections — spread across hosts and
formats, while conventional automated tools frequently act as "black boxes" whose conclusions
cannot be verified against raw evidence. This project addresses that gap by guaranteeing that every
security conclusion is fully transparent and directly traceable to the exact original log lines that
produced it.

**[METHODOLOGY]** The system is built as a six-stage pipeline. First, a React + TypeScript web
frontend ingests log files and transmits them to a FastAPI REST backend. Second, the backend
validates uploads and routes them through a log-ingestion layer built on Pandas and Pydantic v2,
which normalises CSV and real Mordor/Sysmon NDJSON logs into seven typed event categories. Third, a
NetworkX directed **event graph** is constructed using temporal (`followed_by`), process-parentage
(`spawned`), and shared-object (`same_object`) edges within a configurable ±5-minute window. Fourth,
a **symbolic AI reasoning engine** performs rule-based forward chaining, matching a knowledge base
of five MITRE ATT&CK-grounded rules over local graph neighbourhoods until fixpoint convergence
(bounded by a safety cap of ten iterations). Fifth, reconstructed incidents and their evidence
chains are persisted in SQLite. Sixth, the frontend renders the result as an interactive, animated
attack-chain graph using React Flow and the Dagre layout engine.

**[FINDINGS]** The implementation successfully reconstructs multi-stage incidents with complete
evidence trace-back. On the synthetic attack dataset the engine derived four conclusions with
verifiable supporting events, while the benign dataset produced zero conclusions, confirming
negative-case suppression. Two-level forward chaining is demonstrated by a chained persistence rule
that consumes the output of an earlier rule. The automated test suite executes 217 passing tests
(with 7 skipped) across 19 test modules covering parsing, graph construction, rule triggering,
reasoning, configuration, API contracts, and cross-host correlation. On a 10,000-event synthetic
workload the full graph-construction and reasoning pipeline completes within the stated 5-second
budget (measured ≈4.82 s). Real Mordor/OTRF datasets and the multi-host APT29 Day-1 campaign were
ingested successfully, and cross-host correlation linked findings across four hosts. Residual
precision limitations on certain real datasets and explicitly deferred production features are
documented as constraints and future work.

**Keywords:** incident reconstruction, log correlation, symbolic AI, forward chaining, MITRE
ATT&CK, event graph, explainable security analytics.

# CHAPTER-1: PROJECT DESCRIPTION AND OUTLINE

## 1.1 Introduction

Security analysts in a Security Operations Centre (SOC) routinely face thousands of low-level log
events generated by endpoint telemetry, operating-system audit trails, and network sensors. A single
multi-stage intrusion manifests as a long chain of individually innocuous actions — a file download,
the launch of a scripting interpreter, a registry modification, and an outbound connection — that
only becomes meaningful when correlated together. Manual correlation of these disjointed records is
slow, error-prone, and does not scale.

This project, the **AI-Powered Cybersecurity Incident Reconstruction & Analysis System**, ingests
raw logs from multiple hosts and reconstructs them into a single, unified, interactive incident
timeline. The defining characteristic of the system is that it uses **Symbolic AI** — specifically
rule-based **forward chaining** — rather than an opaque machine-learning or large-language-model
classifier. Consequently, every conclusion the platform produces is 100 % transparent and can be
traced back to its originating raw log evidence. The platform thereby serves as both a functional
reconstruction tool and an educational demonstration of explainable security reasoning.

## 1.2 Motivation for the work

The motivation for the project arises from three observations:

1. **Analyst overload.** A typical host can emit tens of thousands of events per day. Isolated
   events such as a PowerShell launch or a registry write are not, by themselves, alerts; their
   significance emerges only from their relationship to other events in time and process context.
2. **The explainability problem.** Numerous automated correlation and detection systems, especially
   those based on neural networks or LLMs, produce a verdict without exposing _why_ that verdict was
   reached. In security operations this is unacceptable: an analyst cannot act on, or defend, a
   conclusion that cannot be justified from evidence.
3. **Fragmentation across hosts and formats.** Evidence of a single campaign is frequently split
   across several machines and encoded in heterogeneous log schemas (custom CSVs, Windows Sysmon
   NDJSON, and network-monitor output). There is a clear need for a lightweight tool that unifies
   these sources without requiring heavy enterprise infrastructure.

These factors motivate a system whose reasoning is deterministic, auditable, and grounded in an
established threat framework (MITRE ATT&CK).

## 1.3 Overview of the Project and Techniques Used

The platform is organised as a six-stage data and control flow that coordinates the frontend, the
backend parsing/reasoning layers, and database storage:

1. **Web frontend (React + React Flow).** The analyst uploads CSV/JSON logs through a browser form;
   the file is transmitted as multipart form data to the API server.
2. **API backend gateway (FastAPI).** A thin REST server validates upload size and file type and
   coordinates routing.
3. **Log ingestion and schemas (Pandas + Pydantic v2).** Raw logs are parsed, timestamps are
   normalised to UTC, malformed rows are handled according to a defined policy, and entries are
   converted into typed `Event` objects.
4. **Relationship graph builder (NetworkX).** A directed event graph is constructed; edges encode
   temporal adjacency within a ±5-minute window and parent-to-child process relationships.
5. **Symbolic AI reasoning engine (forward chaining).** MITRE ATT&CK rules are matched over local
   graph neighbourhoods and iterated until fixpoint convergence, producing chained conclusions.
6. **Database persistence and REST response (SQLite + FastAPI).** Computed incidents and their
   evidence lists are serialised into SQLite and returned as JSON to the React client, which renders
   an interactive, animated threat timeline.

**Core techniques employed:**

- **Symbolic AI / rule-based forward chaining** for explainable inference.
- **Knowledge representation** via a rule registry of five MITRE ATT&CK-mapped rules expressed as
  plain Python functions with a uniform signature.
- **Graph-based correlation** using NetworkX, with explicit edge semantics and negative-case
  suppression to avoid graph explosion.
- **Strongly typed data contracts** using Pydantic v2 to guarantee schema validity between layers.
- **Provenance-preserving ingestion**, where each event carries an immutable identifier of the form
  `file_path:line_number`, enabling end-to-end evidence trace-back.
- **Cross-host correlation** through shared concrete objects (destination IPs, registry keys, file
  paths, and cryptographic hashes), and kill-chain-ordered narrative summarisation.

## 1.4 Problem Statement

Given a set of heterogeneous log files collected from one or more hosts, the system must
automatically: (a) parse and normalise the logs into a common event schema; (b) discover the
relationships between otherwise isolated events; (c) apply interpretable security rules to
reconstruct multi-stage incidents mapped to MITRE ATT&CK; and (d) present each reconstructed
conclusion together with the exact evidence that justifies it, so that a human analyst can verify
every step of the reasoning. The central challenge is to achieve this correlation in a manner that
is both **accurate** (minimal false conclusions on benign data) and **explainable** (every conclusion
traceable to source evidence).

## 1.5 Objective of the work

The objectives of the project are:

1. To design and implement a multi-format log parser that accepts CSV and real
   Mordor/Sysmon NDJSON logs and normalises them into seven typed event categories.
2. To construct a directed event graph whose edges capture temporal proximity, process parentage,
   and shared objects, while deliberately avoiding edge types that cause clique explosion.
3. To implement a forward-chaining symbolic reasoning engine that evaluates a knowledge base of
   MITRE ATT&CK rules over local graph neighbourhoods until a fixpoint is reached.
4. To support **two-level chaining**, in which the conclusion of one rule becomes an input fact for
   another rule, demonstrating genuine multi-stage reasoning.
5. To guarantee **complete evidence trace-back** by assigning stable unique identifiers to every
   conclusion and preserving immutable source identifiers for every event.
6. To provide a REST API and a React-based dashboard that visualises the reconstructed attack chain
   interactively.
7. To validate the system through an automated test suite and real-world datasets, measuring
   precision on benign data and performance on large inputs.

# CHAPTER-2: RELATED WORK INVESTIGATION

## 2.1 Introduction

This chapter positions the project within the broader field of security log analysis and alert
correlation. It first defines the core area of the work, then examines three representative
existing approaches — signature-based SIEM correlation, machine-learning-based detection, and
emerging LLM/AI-agent security assistants — before comparing their advantages and disadvantages and
drawing observations that motivate the chosen design.

## 2.2 Core area of the project

The core area of this project is **security event correlation and incident reconstruction**, a
sub-discipline of security monitoring and digital forensics. It is closely related to Security
Information and Event Management (SIEM) systems, which aggregate and correlate logs, and to the
**MITRE ATT&CK** knowledge base, which provides a standard taxonomy of adversary tactics and
techniques [1], [2], [3]. The project also draws on **alert-correlation** research, which studies
how independent detection events can be linked into higher-level attack scenarios [8], and on the
**Cyber Kill Chain** model, which describes the sequential stages of an intrusion [6]. The specific
contribution of this work is the use of deterministic, graph-local forward chaining to perform that
correlation in a fully explainable way.

## 2.3 Existing Approaches/Methods

### 2.3.1 Approaches/Methods – 1: Signature- and Rule-Based SIEM Correlation

The most widely deployed approach correlates events using predefined detection signatures and
correlation rules. Tools such as Sigma provide a vendor-neutral, human-readable signature format
that can be translated into the query languages of SIEM platforms [4], while commercial and
open-source SIEM platforms apply correlation searches over indexed logs. Detection content is
typically mapped to MITRE ATT&CK techniques [1], [3], and rules may be chained to express multi-step
behaviour. This approach is deterministic and interpretable: a fired rule can be inspected and its
logic audited.

### 2.3.2 Approaches/Methods – 2: Machine-Learning and Anomaly-Based Detection

A second family of approaches treats correlation and detection as a statistical or learning problem.
Supervised models are trained on labelled attack traffic to classify events or flows, while
unsupervised methods (clustering, auto-encoders, isolation forests, sequence models) learn a
baseline of normal behaviour and flag deviations [9]. These methods can generalise to previously
unseen attacks and can operate at high data volumes, and deep-learning sequence models are especially
attractive for capturing temporal patterns across long event sequences.

### 2.3.3 Approaches/Methods – 3: LLM and AI-Agent Security Assistants

A recent and rapidly growing class of approaches applies large language models (LLMs) and autonomous
agents to security operations [10]. These systems summarise alerts, translate natural-language
queries into detection logic, retrieve relevant context from documentation or threat intelligence,
and can propose or even automate investigation steps and response actions [11], [12]. They offer
strong natural-language interaction and can reduce analyst toil by drafting incident narratives and
triage recommendations.

## 2.4 Pros and cons of the stated Approaches/Methods

| Approach                                | Advantages                                                                                       | Disadvantages                                                                                                                                                   |
| --------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Signature / rule-based SIEM correlation | Deterministic, transparent, auditable; mature ecosystem; direct ATT&CK mapping; low compute cost | Cannot detect behaviour outside its rule set; rules require expert authoring and maintenance; correlation logic can become complex and brittle at scale         |
| Machine-learning / anomaly-based        | Generalises to novel attacks; scales to large volumes; learns temporal patterns automatically    | Often opaque ("black box"); high false-positive rates on noisy logs; requires large labelled/representative datasets; results are hard to justify to an analyst |
| LLM / AI-agent assistants               | Natural-language interaction; can summarise and contextualise; flexible and extensible           | Non-deterministic outputs; risk of hallucination; cannot guarantee evidence trace-back; cost/latency and data-privacy concerns; limited auditability            |

## 2.5 Issues/observations from investigation

The investigation yields three central observations that shaped this project:

1. **Explainability is non-negotiable in security operations.** Both machine-learning and LLM
   approaches, however capable, share a common weakness — the difficulty of justifying a conclusion
   from evidence. A rule-based approach, by contrast, can guarantee that every conclusion points
   back to concrete log lines.
2. **Pure signature matching is insufficient.** Isolated signatures do not capture multi-stage
   behaviour. Correlation across events is required, which motivates an explicit event-graph model
   and a reasoning step that chains conclusions together.
3. **Naïve correlation causes graph explosion.** Correlating every pair of events that share a user
   or host produces dense cliques that degrade both visualisation and performance. Effective
   correlation therefore requires disciplined edge semantics that encode only meaningful
   relationships.
4. **Real-format support is essential for credibility.** Any practical system must ingest genuine
   endpoint telemetry (e.g., Windows Sysmon via Mordor/OTRF datasets), not just curated CSVs.

These observations justify the project's focus on deterministic, graph-based, forward-chaining
reasoning with strict provenance preservation.

## 2.6 Summary

This chapter defined the core area of security event correlation and incident reconstruction, and
reviewed three existing approaches — signature/rule-based SIEM correlation, machine-learning
detection, and LLM/AI-agent assistants — comparing their strengths and weaknesses. The key
observation, that explainability and evidence trace-back are paramount and that naïve correlation
causes graph explosion, directly motivates the symbolic, graph-local architecture presented in the
following chapters.

# CHAPTER-4: DESIGN METHODOLOGY AND ITS NOVELTY

## 4.1 Methodology and goal

The design methodology follows a **layered, pipeline-oriented approach**: each stage of the
analysis is an independently testable module with a well-defined contract, and data flows
unidirectionally from ingestion to reasoning to presentation. The overarching goal is to produce an
incident reconstruction whose every conclusion is explainable and reproducible. The guiding design
principle, established at the outset, is that _if the "why?" trace-back works end-to-end, the
project succeeds even with only a few rules; if it does not, no number of rules will save it._

## 4.2 Functional modules design and analysis

The backend is decomposed into the following functional modules:

| Module              | Responsibility                                                                                                                            |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `config.py`         | Central configuration via pydantic-settings with fail-fast validators (CORS origins, size limits, time window, thresholds, database URL). |
| `models.py`         | Pydantic data contracts: `Event`, `Evidence`, `Conclusion`, `Incident`, enumerations, and severity/confidence rules.                      |
| `parser.py`         | CSV ingestion into a `ParseResult`, with bad-row policy, UTC normalisation, and provenance assignment.                                    |
| `mordor_parser.py`  | Mordor/Sysmon NDJSON ingestion, EventID mapping, and key/value parsing of the raw `Message` block.                                        |
| `dispatch.py`       | Content-based format detection and dispatch (`parse_any_log`), plus process-ID normalisation.                                             |
| `normalize.py`      | Canonicalisation of hostnames, IP addresses, and file/registry hashes.                                                                    |
| `graph.py`          | Construction of the directed event graph and its edge semantics.                                                                          |
| `rules/registry.py` | The knowledge base of five MITRE ATT&CK rules as plain functions with a uniform signature.                                                |
| `engine.py`         | The forward-chaining fixpoint reasoning loop, conclusion de-duplication, and clustering.                                                  |
| `correlation.py`    | Cross-host linking, kill-chain ordering, and narrative summary construction.                                                              |
| `orchestrator.py`   | Coordinates the full pipeline and provides the command-line entry point.                                                                  |
| `storage.py`        | SQLite persistence of incidents.                                                                                                          |
| `main.py`           | FastAPI application, REST endpoints, CORS, and background jobs.                                                                           |

Each module has a corresponding test module, allowing the pipeline to be verified layer by layer.

## 4.3 Software Architectural designs

The system follows a **client–server, three-tier architecture**:

1. **Presentation tier** — a React + TypeScript single-page application (with React Flow and the
   Dagre layout engine) that uploads logs and renders conclusions and the attack chain.
2. **Application/logic tier** — a FastAPI REST server that validates uploads and orchestrates the
   ingestion → graph → reasoning → correlation pipeline.
3. **Data tier** — a SQLite relational store that persists reconstructed incidents as JSON.

Within the logic tier, the analysis pipeline is composed of clearly separated stages: parsing
(`parser`/`mordor_parser` via `dispatch`), normalisation (`normalize`), graph construction
(`graph`), reasoning (`engine` + `rules`), correlation (`correlation`), and persistence
(`storage`). A thin orchestrator (`orchestrator`) wires these together, and both the API and the
CLI invoke the same orchestrator to guarantee identical behaviour.

**Architectural decisions and their rationale:**

- **Why an event graph?** Relationships (temporal proximity, parentage, shared objects) are the raw
  material of correlation; expressing them as graph edges makes neighbourhood-scoped reasoning both
  natural and efficient.
- **Why symbolic reasoning instead of ML/LLM?** Determinism and auditability. Forward chaining
  yields a derivation that can be inspected and traced, which is the project's core requirement.
- **Why SQLite?** To avoid heavy container/database orchestration in a student demonstration while
  providing durable persistence. PostgreSQL is documented as a deferred production upgrade.

## 4.4 Subsystem services

**4.4.1 Ingestion and normalisation service.** Converts heterogeneous input into typed events. It
sniffs content to select the correct parser (rather than trusting the extension), extracts the raw
Sysmon `Message` key/value block, maps EventIDs to the internal taxonomy, canonicalises hosts/IPs/
hashes, and stamps each event with its provenance identifier.

**4.4.2 Graph construction service.** Builds a NetworkX directed graph with three edge semantics:
`followed_by` (temporal adjacency within the ±5-minute window, capped to the 15 nearest successors
per event to bound density), `spawned` (parent-to-child processes derived from PID/parent-PID, never
capped because it is sparse and high-signal), and `same_object` (shared file, registry key, or
destination IP, capped at 50 per node). Crucially, edges for `same_user` and `same_host` are
**deliberately omitted**; user and host remain matchable node attributes instead of physical edges.

**4.4.3 Reasoning service.** Executes the forward-chaining fixpoint loop. To keep matching
scalable, a graph index materialises each node's local neighbourhood, candidate lookups by type and
target, and adjacency once per analysis, so rules are evaluated graph-locally rather than against
the entire event set. New conclusions are de-duplicated by a hash of rule identifier, sorted
evidence, and parent conclusion, and the loop terminates on fixpoint or at the ten-iteration safety
cap.

**4.4.4 Correlation and summarisation service.** Clusters equivalent conclusions, orders them by
kill-chain stage and confidence, links conclusions that share concrete objects across hosts, and
produces a narrative summary.

**4.4.5 Persistence and API service.** Serialises incidents to SQLite and exposes them through REST
endpoints (`POST /upload`, `POST /analyze`, `GET /jobs/{id}`, `GET /incident/{id}`), with background
processing for large inputs.

## 4.5 User Interface designs

The dashboard is a single-page application with two primary states:

- **Landing/Upload state** — a hero section, a brief explanation of the three-step workflow, and a
  drag-and-drop upload form that performs client-side extension and size checks and shows progress
  and error feedback.
- **Result state** — a summary bar (number of conclusions, evidence chains, and cited events), a
  tactic legend, and a tab toggle between two views:
  - **Conclusions view** — a card per conclusion, each showing technique, tactic, severity,
    confidence, rule identifier, affected hosts, and an expandable evidence panel with clickable
    event identifiers and a "derived from" link to any parent conclusion.
  - **Attack Chain view** — an interactive React Flow canvas in which conclusions are nodes laid out
    left-to-right by Dagre, connected by animated parent-to-child edges, with zoom, pan, minimap,
    and a dark colour mode.

The visual language uses a dark SOC theme for sustained readability.

**Novelty of the design.** The novelty of this project lies in the combination and disciplined
execution of the following ideas:

1. **Graph-local symbolic forwarding chaining** — rules are matched over pre-materialised local
   neighbourhoods rather than the whole event set, combining explainability with scalability.
2. **Negative-case suppression** — by deliberately refusing to draw `same_user`/`same_host` edges,
   the design prevents clique explosion while retaining those attributes for rule matching. This is
   a deliberate anti-pattern avoidance decision rather than an oversight.
3. **Stable unique conclusion instance-IDs** — assigning a UUID to every conclusion (rather than
   referencing the rule template identifier) allows multi-level dependencies to be rendered without
   collisions when a rule fires multiple times, and enables true chained reasoning.
4. **End-to-end provenance** — immutable `file:line` event identifiers plus per-conclusion evidence
   lists make every inference auditable back to raw data.

novel elements — graph-local forward chaining, negative-case suppression, stable conclusion
identifiers, and end-to-end provenance.

# CHAPTER-5: TECHNICAL IMPLEMENTATION & ANALYSIS

## 5.1 Outline

This chapter describes the concrete implementation of the system: the technical coding solutions,
the working layouts of the interface, the prototype, the test and validation strategy, and the
performance analysis with supporting data and charts.

## 5.2 Technical coding and code solutions

**5.2.1 Data contracts.** All inter-layer data is defined with Pydantic v2 models. An `Event`
carries its type, timestamp, actor, source host, target object, provenance identifier, and
metadata. A `Conclusion` carries a stable UUID, rule identifier, technique and tactic, confidence,
severity, hosts, supporting evidence, and an optional parent conclusion identifier. This enforces
schema correctness at every boundary.

**5.2.2 Parsing and dispatch.** `parse_any_log` detects the format from file content rather than the
extension. CSV rows are parsed through a bad-row policy that collects diagnostics instead of
aborting, and timestamps are normalised to UTC. The Mordor parser reads NDJSON lines, extracts the
multi-line `Message` string, splits it into `Key: Value` pairs, and maps Sysmon/Windows EventIDs to
the internal taxonomy. Each event receives the identifier `source_file:line_number`, assigned before
sorting so that identifiers always point to the original source line.

**5.2.3 Graph building (implementation).** `build_graph` iterates over sorted events, adding
`followed_by` edges to the nearest successors within the time window, `spawned` edges from
PID/parent-PID relationships (with tolerant PID normalisation for integer, string, and float
encodings), and `same_object` edges between events sharing a target. Because NetworkX directed
graphs cannot hold parallel edges, pairs with multiple relationship kinds store a list of kinds and
are read through an accessor.

**5.2.4 Reasoning engine (implementation).** The engine builds a `_GraphIndex` once, then loops up
to `MAX_ITERATIONS = 10` times. In each pass it feeds every rule the local neighbourhood of each
node together with the accumulated facts. Rules have the uniform signature
`(neighborhood, graph, facts) -> Conclusion | None`, so new rules can be added without altering the
engine. New results are de-duplicated by `hash_conclusion`, and the loop terminates on fixpoint or
at the cap. After the loop, `cluster_conclusions` merges equivalent conclusions and unions their
evidence and hosts.

**5.2.5 Knowledge base.** The system ships five rules:

| Rule ID                  | MITRE Technique | Tactic              | Trigger                                                                                                                      | Confidence |
| ------------------------ | --------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------- |
| `REG-PERSIST-01`         | T1547.001       | Persistence         | Process execution followed by modification of a known autostart registry location within the window                          | 0.6 / 0.4  |
| `PSH-STAGING-01`         | T1059.001       | Execution           | PowerShell execution followed by a file download within the window                                                           | 0.5        |
| `PERSIST-ESTABLISHED-01` | T1547.001       | Persistence         | **Chained:** consumes the `PSH-STAGING-01` conclusion plus a nearby registry modification, asserting an established foothold | 0.8        |
| `C2-BEACON-01`           | T1071           | Command and Control | Process execution followed by an outbound connection to a public, non-common destination port within the window              | 0.3        |
| `LOG-CLEAR-01`           | T1070           | Defense Evasion     | Detection of a log-deletion event signature                                                                                  | 0.9        |

**5.2.6 Unique identifiers and trace-back.** Every conclusion is issued a `uuid.uuid4().hex`
identifier, and a chained rule stores the parent conclusion's UUID (not the rule identifier) in
`parent_conclusion_id`. This is the concrete implementation of the fix for rendering collisions and
is what makes multi-level dependency graphs correct.

**5.2.7 API implementation.** The FastAPI application exposes `POST /upload` (validation and secure
temporary storage), `POST /analyze` (parse-once, then either synchronous analysis or a background
job returning an HTTP 202 with a job identifier), `GET /jobs/{id}` (job status and result), and
`GET /incident/{id}` (incident retrieval). Errors are mapped to appropriate status codes (413 for
oversized uploads, 400 for invalid filenames/extensions, 422 for unknown formats, 404 for unknown
identifiers).

**5.2.8 Persistence.** SQLite stores incidents in a single table as JSON produced by
`Incident.model_dump_json()` and rehydrated with `model_validate_json`, using insert-or-replace
semantics.

# CHAPTER-6: PROJECT OUTCOME AND APPLICABILITY

## 6.1 Outline

This chapter summarises the key implementations of the system, the significant outcomes achieved,
and the applicability of the project to real-world scenarios.

## 6.2 Key implementations outlines of the System

1. **Multi-format, provenance-preserving ingestion** supporting CSV and real Mordor/Sysmon NDJSON,
   with content-based format detection and immutable `file:line` source identifiers.
2. **A disciplined event-graph model** with three edge semantics, explicit edge caps, and
   negative-case suppression of user/host edges to prevent clique explosion.
3. **A graph-local forward-chaining engine** with a uniform rule interface, de-duplication,
   fixpoint convergence, a ten-iteration safety cap, and conclusion clustering.
4. **A five-rule MITRE ATT&CK knowledge base**, including a two-level chained rule that consumes a
   prior conclusion to assert an established foothold.
5. **Stable unique conclusion identifiers** enabling correct multi-level dependency rendering and
   precise evidence trace-back.
6. **Cross-host correlation** through shared destination IPs, registry keys, file paths, and hashes,
   plus kill-chain-ordered narrative summarisation.
7. **A REST API with background processing** for large inputs, SQLite persistence, and a React
   dashboard with an interactive React Flow / Dagre attack-chain visualisation.

## 6.3 Significant project outcomes

- **Explainable reconstruction achieved.** Every conclusion carries evidence and a rule identifier
  that resolve to concrete source log lines, satisfying the project's central requirement.
- **Correct positive and negative behaviour.** Attack data yields conclusions; benign data yields
  none, validating precision on the negative case.
- **Multi-stage reasoning demonstrated.** The chained persistence rule proves that the engine can
  build higher-level conclusions from earlier ones.
- **Real-data viability demonstrated.** Public Mordor/OTRF datasets and a four-host APT29 campaign
  were successfully ingested and correlated.
- **Verification rigor.** A 19-module suite executing 217 passing tests (7 skipped) plus golden
  precision bounds and a shared API contract test provides strong regression protection.
- **Performance budget met on synthetic data** (≈4.82 s for 10,000 events) with bounded graph
  density.

## 6.4 Project applicability on Real-world applications

The system is directly applicable to several real-world contexts:

1. **SOC alert triage and incident triage.** It converts raw, multi-source telemetry into a
   concise, evidence-backed incident narrative, accelerating analyst triage.
2. **Digital forensics and post-incident review.** Because every conclusion is traceable to source
   log lines, the output can serve as an auditable reconstruction for post-incident reporting.
3. **Security training and education.** The platform is an ideal teaching tool for demonstrating
   attack-chain concepts, MITRE ATT&CK mapping, and explainable reasoning to students and junior
   analysts.
4. **Threat-hunting and detection engineering.** Analysts can author new rules in the uniform rule
   interface and immediately observe their effect on real datasets, supporting detection
   development and tuning.
5. **Lightweight/edge deployments.** With a file-based SQLite store and modest resource footprint,
   the system is suitable for environments that cannot host a full enterprise SIEM.

The deferred production capabilities (PostgreSQL, authentication/RBAC, containerisation, CI/CD, and
real-time streaming) are the natural next steps required to deploy the system at enterprise scale.

## 6.5 Inference

The outcomes confirm the project's core thesis: a deterministic, graph-based symbolic reasoning
approach can reconstruct multi-stage incidents while remaining fully explainable and auditable. The
combination of bounded graph construction, graph-local forward chaining, and end-to-end provenance
delivers practical reconstruction without sacrificing interpretability.

# CHAPTER-7: CONCLUSIONS AND RECOMMENDATION

## 7.1 Outline

This final chapter states the limitations and constraints of the system, proposes future
enhancements, and presents the concluding inference of the project.

## 7.2 Limitation/Constraints of the System

1. **Residual false positives on some real datasets.** Despite clustering and bounding, certain
   rules — notably the command-and-control and registry-persistence rules — still over-report on
   specific real datasets (e.g., a log-clear dataset producing spurious C2/persistence conclusions).
   Precision on real data remains "met in quantity, not always in quality."
2. **Scale.** Large real datasets (tens of thousands of events) are memory- and time-intensive
   (hundreds of megabytes and tens of seconds to minutes), which is acceptable for demonstration but
   not for high-throughput production.
3. **Chained reasoning not yet demonstrated on real campaigns.** Two-level forward chaining is
   proven on synthetic data; the specific prerequisite rules did not fire on the APT29 Day-1
   campaign, so chaining is under-demonstrated on real data.
4. **Single-host rule scope by design.** Rules match within a host, and cross-host linkage depends
   on shared concrete objects; correlation purely by time proximity across hosts is intentionally
   not performed.
5. **No authentication or rate limiting.** The demonstration accepts public uploads on localhost;
   an API key is configurable but not enforced, so production deployment requires network or proxy
   protection.
6. **SQLite-only persistence.** The storage layer does not support PostgreSQL URLs, and ephemeral
   filesystems would reset incident history on redeploy.
7. **Frontend last-mile gaps.** There is no client-side routing or shareable incident URLs, no
   dedicated data-fetching layer, and only a contract test rather than full component tests.
8. **Taxonomy and dataset limitations.** Some real datasets do not contain the specific event
   signatures a given rule expects, so expected rules do not fire; coverage is limited to the seven
   defined event types and five rules.
9. **Dependency reproducibility.** The pinned dependency set is bleeding-edge relative to the
   documented Python 3.11 baseline, which may complicate reproduction on other machines.

## 7.3 Future Enhancements

1. **Improve rule precision** through richer contextual guards (allow-lists of benign destinations,
   process-lineage checks, and suppression of common administrative activity) and by learning
   confidence thresholds from validation data.
2. **Expand the knowledge base** with additional MITRE ATT&CK techniques and support authoring
   rules in a declarative DSL rather than code.
3. **Prove chaining on real campaigns** by selecting/curating campaign subsets in which prerequisite
   and chained rules both fire, and by adding multi-hop correlation.
4. **Scale the pipeline** via incremental/streaming graph construction, partitioned reasoning, and a
   production-grade database (PostgreSQL) with migrations.
5. **Add authentication, RBAC, rate limiting, and a health endpoint**, and provide containerised
   deployment (Docker/Compose) with CI/CD.
6. **Enhance the frontend** with client-side routing and shareable incident URLs, a data-fetching
   cache, light/dark theming, and comprehensive component tests.
7. **Real-time ingestion** through streaming agents (e.g., Sysmon/Zeek forwarders) instead of batch
   uploads.
8. **Optional ML/LLM augmentation** as a _candidate-generator_ layer whose suggestions are always
   validated by the symbolic engine, preserving explainability while improving recall.
9. **Expand dataset coverage** and publish reproducible benchmark scripts and campaign golden
   outputs.

## 7.4 Inference

The project successfully met its central objective: it reconstructs multi-stage security incidents
from heterogeneous, multi-host logs using transparent, deterministic, rule-based forward chaining,
and it guarantees that every conclusion is traceable to its raw evidence. The system is lightweight,
well-tested, and demonstrably functional on both synthetic and real data sets. While precision on
some real datasets, scalability, and several production features remain to be improved, the
foundational design — bounded event graphs, graph-local symbolic reasoning, stable conclusion
identifiers, and end-to-end provenance — provides a sound and extensible platform for explainable
incident reconstruction. It is therefore recommended as an effective educational and triage tool,
and as a strong base for the production-oriented enhancements outlined above.
